# Petrol Station Restock Order Automation

An end-to-end **business process automation system** built with n8n to streamline restocking requests for petrol-station convenience shops.

The system automatically receives shop-attendant restock requests, identifies the product categories mentioned, validates incoming messages, routes orders to a configured supplier, and monitors supplier replies for follow-up.

The workflow is **self-hosted and always-on**, running on a free Oracle Cloud VPS.

## The Business Process

A procurement coordinator oversees restocking for convenience shops located at petrol stations.

Shop attendants submit restock requests by email. A single request can contain products from multiple categories, requiring the coordinator to manually:

1. Review the incoming request
2. Identify the product categories
3. Process the order
4. Send the order to the supplier
5. Monitor the supplier's response
6. Follow up when necessary

This creates repetitive manual work and introduces opportunities for delays, missed responses, or inconsistent processing.

## The Problem

The restocking process relied on manually reading and processing incoming emails.

For example, an order might contain products from several categories such as snacks, beverages, and toiletries. The procurement process therefore requires the incoming request to be interpreted before it can be forwarded.

The workflow also needs to distinguish genuine shop-attendant orders from unrelated emails, replies, spam, and messages generated by the automation itself.

## The Solution

I designed an always-on **n8n workflow** that automates the repetitive email-processing and supplier handoff stages of the process.

The current workflow:

1. **Monitors the procurement inbox** for new incoming order emails.
2. **Identifies product categories** mentioned in each order.
3. **Validates the incoming message** to verify that it comes from a known shop attendant and is not spam, a reply, or an email generated by the workflow itself.
4. **Routes the order to a configured supplier** automatically.
5. **Monitors supplier responses** and sends a flagged notification when a supplier reply requires attention.

The automation runs without requiring the procurement coordinator to manually trigger the workflow.

## Key Design Decisions

### 1. Category detection before routing

A single restock email can contain multiple product categories.

Instead of treating the email as a single generic request, the workflow first identifies which categories are present. This creates a structured representation of the order that can be used by later routing logic.

The current implementation sends the resulting order to one configured supplier, but the category-level structure provides a foundation for future supplier-specific routing.

### 2. Using Switch/conditional logic for category handling

The workflow uses conditional routing logic to determine how different product categories should be handled.

This was preferable to creating one large block of hard-coded logic because each category can be maintained and extended independently.

The approach also makes the workflow easier to adapt if supplier relationships change in the future.

### 3. Sender validation and message filtering

One of the requirements was ensuring that the workflow only processes legitimate shop-attendant orders.

The workflow therefore checks incoming messages before processing them, including validation designed to prevent:

- Unrecognized senders
- Spam or unrelated messages
- Replies that should not start a new order workflow
- Emails generated by the automation itself

This prevents the workflow from blindly processing every message that reaches the inbox.

### 4. Whitelist logic and a validation bug

During testing, the message-validation logic exposed an important edge case.

The initial filtering approach behaved incorrectly because a condition intended to identify allowed senders could produce the opposite result when combined with the workflow's conditional logic.

I corrected the validation by changing the logic to explicitly treat **known shop-attendant addresses as the allowed set**, rather than relying on a blacklist-style assumption.

This reinforced an important automation principle: **validation logic should be tested against both positive and negative cases**, not only against the expected successful input.

### 5. Designing for unattended execution

The workflow was designed to operate without someone manually opening n8n and pressing **Execute**.

The deployed system continuously monitors the relevant inbox and processes qualifying messages automatically.

This distinction was important because the goal was not simply to demonstrate an n8n workflow, but to build an **operational automation that could run continuously in a real environment**.

## Technology Stack

- **n8n** — workflow orchestration and automation
- **PostgreSQL** — database
- **Docker / Docker Compose** — containerized deployment
- **Caddy** — HTTPS and reverse proxy
- **Oracle Cloud Always Free VPS** — cloud infrastructure
- **Email integrations** — order intake, supplier communication, and response monitoring

## Deployment

The complete system is self-hosted on an **Oracle Cloud Always Free Ubuntu ARM VPS**.

The deployment uses Docker Compose to run the application stack, including:

- n8n
- PostgreSQL
- Caddy

The server is configured as an always-on automation environment, allowing the workflow to process incoming orders without requiring a local computer to remain running.

## Testing & Verification

The deployed workflow was tested using an end-to-end scenario designed to simulate the actual business process.

A test order was:

1. Sent from a separate device
2. Received by the procurement inbox
3. Automatically processed by n8n
4. Checked against the workflow's validation logic
5. Categorized based on the products mentioned
6. Forwarded to the configured supplier
7. Followed through the supplier-response stage

The test was completed **without manually executing the workflow in n8n**.

This verified that the deployed automation could receive and process an order unattended and trigger the supplier communication as expected.
